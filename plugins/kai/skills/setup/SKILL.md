# Set up Kai

Get this repository ready for Kai in a few minutes, without anyone having to know the options. `kai init` does the writing and never overwrites your changes: when one of Kai's files differs from the new version, it writes `<file>.kai-new` beside it for you to merge (a workflow that differs only in the action versions Kai pins is updated in place).

Write everything a person reviews by `${CLAUDE_PLUGIN_ROOT}/references/writing.md`.

## 1. Look before asking

- The working directory must be a git repository. If `.kai/config` already exists, this is an **upgrade**: read the current `KAI_LEVEL` and settings from it, and skip to step 3 with `--dry-run` so the person sees what would change. `kai init` never touches their `.kai/config` or `.kai/tiers`, so if the person asks for a different level than the current `KAI_LEVEL`, set it in `.kai/config` yourself and pass the same `--level`. Do the same for `KAI_SHIP` and `--ship`, and add the `KAI_SHIP` line (with the comment `kai init` writes) when the config predates it. `kai init` creates `REVIEW.md` and `.claude/skills/steward/SKILL.md` once and never changes them, because the team owns both: compare each with its template under `${CLAUDE_PLUGIN_ROOT}/template/`, and offer to merge what Kai changed. If `.kai/config` still sets `KAI_PROD_DEPLOY_PATTERN`, nothing enforces it any more: offer the permission rule in step 3 in its place, then delete the line. If the repository has git hooks (`.pre-commit-config.yaml`, `.husky/`, `lefthook.yml`), say that Kai no longer blocks a command that skips them and that a `/steward` watch commits with git hooks off, and offer to add what they check to `KAI_VERIFY_CMDS` in `.kai/config`.
- On an upgrade, if `.claude/settings.json` sets `permissions.defaultMode` to `plan`, say that Kai before 0.10.0 set it so that every session started in plan mode, and offer to remove it: `/kai:implement` now enters plan mode itself, and other requests no longer need it. Remove it only if the person agrees, since they may have set it themselves.
- Work out sensible defaults from the repository, so the questions are confirmations rather than blanks:
  - **Ticket system and prefixes:** look at branch names and recent commit messages (`git branch -a`, `git log --oneline -50`) for keys like `PAY-123` (Jira or Linear) or `#42` (GitHub).
  - **Test commands:** look at `package.json` scripts, `Makefile`, `pyproject.toml`, `go.mod`, `Cargo.toml`, or CI workflows. Prefer the commands CI already runs, including lint and type checks, one per line. Prefer a script or target that the repository's own manifests define (`npm test`, `make check`) over a bare tool call: a `/steward` watch takes from the steward rules only which of those to run. If the repository has git hooks (`.pre-commit-config.yaml`, `.husky/`, `lefthook.yml`), include what they check: a `/steward` watch commits with git hooks off, so a check that lives only in a git hook never runs on its commits.
  - **CI:** GitHub Actions is used if `.github/workflows/` exists or the `origin` remote is on GitHub. Otherwise plan on `--no-ci`. Kai's workflow runs the gates, not your tests: those already run locally and in the repository's own CI. If no workflow runs the tests on a pull request, the evidence is only what the author's session reported: propose adding the toolchain steps and `gates: ticket-ref definition tests-locked contract verify` to `kai.yml`, so CI runs `KAI_VERIFY_CMDS` itself.
  - **How to run the application:** look for a dev server, a CLI entry point, a simulator, a compose file, or an existing `verify` skill under `.claude/skills/`. Step 5 writes the skill from this.
  - **Claude Ship** (`--ship`): whether an Owner of the Claude organization has turned on Claude Code Review for this repository, and PR Steward. They need a Claude Team or Enterprise plan and the Claude GitHub App, and are not available with Zero Data Retention, the HIPAA configuration, or customer-managed encryption keys. A developer cannot see those settings, so look for evidence: a `Claude Code Review` check on a recent pull request (`gh pr checks <n>`) for Code Review, and a `claude-pr-steward-watching` label for PR Steward. Plan with `--ship` when Code Review is on, by that evidence or the person's word. With it, Claude Code Review replaces Kai's review workflow and its two agents, and Kai asks PR Steward to look after each change PR. An Owner turns Code Review on first, so PR Steward can be off for a while: Kai's request then has no effect, and the person starts a `/steward` watch, as without Claude Ship. Without `--ship`, Kai adds its own review workflow at level 3 and above, and the person starts a `/steward` watch in Claude Code.
  - **An existing Claude review workflow** (one using `anthropics/claude-code-action` for PR review): without Claude Ship, at level 3 and above, Kai adds its own review workflow. Point out the overlap and ask whether to keep both. Kai's review keeps its own single comment (marked `<!-- kai-review -->`, posted by `github-actions[bot]`), so the two coexist without overwriting each other, but two reviews on every PR may be one too many. If the person keeps only theirs, delete `.github/workflows/kai-review.yml` after step 3. One well-tuned reviewer finds more than two stacked ones: tune `REVIEW.md` before adding a reviewer.
  - **Review credentials:** without Claude Ship, Kai's review reads an `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` repository secret, and skips with a notice when neither exists.
- Check `gh auth status`. For a private marketplace, git must also clone without a prompt (`gh auth setup-git`). A `/steward` watch needs Claude Code 2.1.330 or later (`claude --version`), GitHub CLI 2.63 or later, and git 2.38 or later: name any that is too old.

## 2. Confirm with the person

Ask in one batch (AskUserQuestion when available), with your detected defaults preselected:

- Ticket system (`jira`, `linear`, or `github`) and project prefixes.
- The commands that must pass before work is done.
- Whether Claude Code Review is on for this repository, and whether PR Steward is, with what step 1 found preselected.
- The commands that deploy to production, if Claude could ever run one.
- The adoption level, from `$ARGUMENTS` if given. Recommend **1** for a team new to Kai: implement and prove, with guardrail hooks. Raise it later by re-running setup. Level 2 adds specs and risk tiers, 3 adds locked tests and AI review, 4 adds acceptance, retros, and metrics.

## 3. Preview, then write

Run `kai init --dry-run` with the answers (`--provider`, `--prefixes`, `--verify` once per command, `--level`, `--ship` with Claude Ship, and `--no-ci` if there is no GitHub Actions) and show what it would write. Then run it without `--dry-run`. `kai init --help` lists every option. Use `--marketplace <path>` only when testing Kai from a local clone.

Say that the settings it writes deny `gh pr merge` and adding the `kai:tests-changed` label, and make Claude ask before a push to the base branch. For each file it says is not used with Claude Code Review (Kai's review workflow and its two review agents), offer to delete it.

For each production deploy command the person named, add `Bash(<command> *)` to `permissions.ask` in `.claude/settings.json`. Claude then asks a person before it runs that command, in auto mode too. The rule matches the command as written, so a script that wraps the deploy needs its own rule. PR Steward's cloud session may not load the repository's permission rules, so keep production credentials out of the environment it runs in. This is a permission rule and not a Kai hook on purpose: `/ship` and `/steward` refuse to start a watch in a repository that brings a plugin with a hook on shell commands, so Kai has none.

## 4. Set the risk tiers

`.kai/tiers` maps paths to `low`, `medium`, or `high`; anything unlisted is medium. Scan the repository for surfaces that deserve `high` (authentication, authorization, payments, secrets, migrations, public API definitions, infrastructure, `.github/workflows/`), propose the exact lines, and add the ones the person agrees with. Getting this right matters from level 2, because the tier decides which changes need a spec and which need a human code read.

## 5. Write the verify skill

`/kai:prove` runs the change end to end before the pull request, and it needs to know how. Write that down once as a project skill, `.claude/skills/verify/SKILL.md`, so every session starts and drives the application the same way. Keep an existing one, and offer to improve it.

- Its frontmatter has `name: verify` and a `description` that says to use it to run and observe a change before committing. Leave model invocation on: Claude must be able to use it.
- Its body says how to start the application (the command, the port or binary, how to know it is ready, test accounts and seed data that are synthetic), how to drive it (the browser tools for a screen, `curl` for an endpoint, the command for a tool, a simulator for mobile), what a healthy run looks like, and how to stop it. It ends with: report each step you ran and what you saw, and never report success without them.
- Run it yourself before you commit it: start the application, do one real action, and stop it. Fix the skill until that works twice in a row. A smoke test that fails for its own reasons teaches Claude to ignore it.
- Keep it fast. A slow step belongs in a note about when to run it, not in every run.
- For a large repository, put a `verify` skill in a `.claude/skills/` folder near each application, and say in each which paths it covers.
- A library with nothing to start needs no skill. Say so, and `/kai:prove` records `No end-to-end run` with that reason.

## 6. Fill the review checks (level 3)

`REVIEW.md` holds what the reviewer looks for in this repository. Ask the people who own the code for the failures that matter most, and write each as a row of its **Checks** table: a trigger a diff can show, the question to ask, and the incident or PR behind it. Three good rows beat twenty vague ones. On an upgrade, an existing `REVIEW.md` without a Checks table is left alone by `kai init`: offer to add the table from `${CLAUDE_PLUGIN_ROOT}/template/REVIEW.md`.

## 7. Commit and hand off

- Commit the setup on a branch named `kai-setup` with the message `Set up Kai (level <N>)`, and suggest opening a pull request so the team sees it. Branches starting with `kai-setup` need no ticket key, so the setup PR passes Kai's own checks.
- Tell the person what happens next:
  - Teammates who open the repository in Claude Code are prompted to install Kai.
  - A change must not be able to change the checks that judge it. Kai's gates and review already read `.kai/config`, `.kai/tiers`, `REVIEW.md` and the review agents from the base branch, and Claude Code Review never reads `REVIEW.md` from the pull request, but a workflow file runs as the pull request has it. Propose a `CODEOWNERS` entry that gives `.github/workflows/`, `.kai/`, `REVIEW.md` and `.claude/` to the tech lead, and tell the person to require code-owner review in branch protection.
  - To add a gate to a repository that is already in use, list it in `KAI_OBSERVE` in `.kai/config` first. An observed gate reports what it would have blocked and never fails the check. Read a week of its reports, fix the false alarms, then remove it from `KAI_OBSERVE`.
  - On GitHub, a repository admin protects the base branch: require a pull request, an approval, a new approval after every push (`Dismiss stale pull request approvals when new commits are pushed`, or approval of the most recent push), resolved conversations, and the `kai` check. Steward pushes fixes after people have reviewed, so without the new-approval rule its later commits merge on an earlier approval. Require the check that runs the team's tests too (its own workflow, or `kai` with the `verify` gate): a watch's commits skip git hooks, so CI is where the checks hold. Branch protection and rulesets need a paid GitHub plan for private repositories; until then, only Kai's permission rules stand in the way of a push to the base branch.
  - From level 2, `/kai:spec` writes the plan into the Definition PR, and merging it approves the plan. When `/kai:implement` asks to approve a plan instead (level 1, a low-tier change, or a fix), approve it with "Yes, and use auto mode", so Claude carries the work to the pull request without asking again.
  - With Claude Ship, in the order Anthropic's rollout guide gives. First agree a budget: Code Review and PR Steward bill the organization's usage credits, and PR Steward has no spend limit of its own until an Owner sets its monthly limit and the repository's spend cap. Next the repository admin protects the base branch as above, with the Claude GitHub App off the bypass list, before PR Steward works on any PR. Then an Owner of the Claude organization keeps Code Review on for the repository and sets PR Steward to **Manual**, because Kai asks for it on each change PR. PR Steward acts on what reviewers write, so it is for repositories whose collaborators the team trusts.
  - Claude Approvals is optional, and comes last. `kai init` writes no policy: merging `.claude/approvals.yml` turns Claude Approvals on for the repository, so an Owner of the Claude organization agrees first. When they do, load the bundled `claude-approvals` skill and ask it for a first policy in observe mode, in a pull request of its own on a branch whose name starts with `kai-setup` (for example `kai-setup-approvals`), which Kai's gates exempt, with these wishes: one person who is not an author approves every change; Claude comments and never approves; Code Review keeps running on every pull request; and the rule also holds in a directory that has a policy of its own. Name the `high` paths in `.kai/tiers` as the ones that must always take a person. A tiers pattern crosses folders and an Approvals pattern does not: `src/auth/*` is `src/auth/**` there, and `*.sql` is `**/*.sql`. The skill counts the people with write access first, because a policy can lock a small team. The `kai` check stays required on its own, since Approvals cannot read CI results or labels. If the skill is missing, update Claude Code: do not write a policy by hand.
  - Without Claude Ship: after `/kai:implement` opens a pull request, the person types `/steward +github-actions`, and Claude Code looks after the PR from that session for up to seven days. It needs auto mode. It runs the repository's code on their computer with their credentials, so it is only for a repository where they trust everyone who can merge to the base branch. The watch keeps its session and checkout, so they start the next ticket in a second clone of the repository. A worktree is not enough: it shares git's settings, and a `git push -u` there ends the watch. Steward never proves a change: after it pushes a code fix, they pull the branch and run `/kai:prove <KEY>`.
  - Start the first change with `/kai:spec <KEY>`.
- If any `*.kai-new` files were written, list them and offer to merge each one. Until a workflow or agent `.kai-new` is merged, CI keeps running the old file, so the upgrade isn't finished. Require the `kai` check only once the new `kai.yml` is in, since an older one reports its check under another name.
