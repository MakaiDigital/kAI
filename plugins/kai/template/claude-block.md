## How we deliver (Kai)

- Kai's workflow (ticket, spec, plan, failing tests, evidence, pull request) runs only when someone types one of its commands: `/kai:spec`, `/kai:implement`, `/kai:prove`, `/kai:accept`, `/kai:retro`, or `/kai:adr`. Otherwise, handle the request directly, without specs, plans, or evidence files. If someone asks for that work in words, name the command that does it.
- In every session: never push to the base branch, merge or approve a pull request, add the `kai:tests-changed` label, or bypass git hooks. There are two exceptions. A ticket's `<KEY>: failing tests` commit during `/kai:implement` may use `--no-verify` when a hook rejects it only because the new tests fail. In a `/ship` or `/steward` watch, Claude Code requires commits and pushes in the form `git -c core.hooksPath=/dev/null ...`, with git hooks off. Run the checks in `KAI_VERIFY_CMDS` before each push there.
- This repository's `kai` CI check needs a ticket key in the branch name or pull request title, and from level 2 a merged spec and plan for medium and high tier code.
