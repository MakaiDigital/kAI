# kAI

The repository for Kai's Claude Code plugins (`plugins/kai`, `plugins/kai-product`), the `makaidigital` marketplace, and the CI action. `kai init` (driven by `/kai:setup`) sets up a repository.

## Check before committing

```sh
shellcheck plugins/kai/bin/kai plugins/kai/scripts/*/*.sh
shellcheck -s bash plugins/kai/evals/*/scaffold.sh plugins/kai/evals/_fixture/make_repo.sh
bats tests/bats
claude plugin validate . && claude plugin validate plugins/kai && claude plugin validate plugins/kai-product
```

## Gotchas

- Keep it simple. Add a gate or script only for a rule that must always hold and that GitHub (branch protection, reviews, CODEOWNERS) cannot enforce. Otherwise put it in a skill.
- `plugins/kai/scripts/**` are sourced by `bin/kai`, not executed, so variables cross files. That is why each script's `# shellcheck` header disables SC2034/SC2154. Keep those disables per file, never in `.shellcheckrc`.
- Scripts must run under POSIX `sh`, and tests under macOS bash 3.2: no negative array indexes, no `timeout`, and `sed -i` only with a backup suffix.
- CI's Ubuntu job installs shellcheck 0.9.0 from apt, which still flags notes that brew's 0.11 doesn't (for example SC2015 on `A && B || C`). Write an `if` instead, or check with 0.9.0 before pushing.
- In `bin/kai`, the hook preamble reads fields from a heredoc that drops trailing empty lines. Every `read` there needs `|| :`, or hooks die under `set -e` when a field is empty.
- Plugin `dependencies` belong on the marketplace entry, never in `plugin.json`. Declared in the manifest, they stop the plugin loading anywhere they aren't installed, including `claude plugin eval` runs.
- Superpowers and `mattpocock-skills` (the `grilling` skill `/kai:spec` interviews with) are listed through a `git-subdir` source pointing at a skills folder, with the chosen skills named on the entry. That is how we load a subset without hooks or unrelated skills; `strict: false` cannot do it. `skills.bats` checks that every upstream skill a skill names is pinned there.
- `plugins/kai-product/templates/*` and `references/writing.md` must stay byte-identical to their `plugins/kai/` copies (a test checks). A top-level `bin/` stops claude.ai and Cowork from installing `kai-product`, chat ignores hooks, and its skills can't run `kai`.
- Bump `version` in a plugin's `plugin.json` whenever you change it (CI checks). Installed users only receive a new version. Merging to main tags `v<version>` (CI), and `kai init` pins repositories to the commit that tag points at, so a version with no tag breaks every new install.
- Skill evals (`claude plugin eval plugins/kai --scaffold --allow-tools Bash Write Edit --trust-plugin`) cost real model calls. On macOS the eval sandbox breaks Apple's git wrapper, so the cases that commit only pass on Linux.
- `kai init` copies `contract-reviewer.md` and `spec-critic.md` from `plugins/kai/agents/` into repositories (level 3, without `--ship`) so the CI review needs no plugin install. `definition-reviewer.md` runs only from `/kai:spec`. Keep every agent self-contained all the same (no `kai` commands or plugin paths; `product.bats` checks). `template/.claude/skills/steward/SKILL.md` is written at every level for PR Steward, which runs in the cloud without the plugin: keep it self-contained too, with no `kai` command to run (`skills.bats` checks). A watch takes from it only which of the repository's own scripts to run, and runs no skill, so Steward never refreshes the evidence: the author proves again after its fix. Like `REVIEW.md`, it is created once and then belongs to the team, so a fix to the template reaches an existing repository only when `/kai:setup` offers to merge it.
- Skills, templates and scripts share literal strings: the `<KEY>: failing tests` subject, `Result: **PASS**`, the `kai verify on commit <sha>` line, the plan's `## Tests` table, the `## Planned tests`, `## Observed` and `## Contract` tables, the `Verified: checks` commit trailer, the contract gate's `describes an earlier commit` message, the `/steward +github-actions` line a person types, the `Checks run:` and `Needs a person:` review lines, the `## Checks` table in `REVIEW.md`, the `<!-- kai-review -->` and `<!-- kai-gates -->` markers, the `⚠` open-question marker the definition gate looks for, the `Reviewed commit <sha> · review <n>` line (the review workflow reads its own previous one to count reviews), and the `Important`, `Nit` and `Pre-existing` finding tags. Change both sides together.
- A new gate starts in `KAI_OBSERVE` (it reports and never fails the check), and the CI review waits for the `kai` check and skips a commit it failed. The review workflow's tests extract its `run: |` steps by position, so adding one renumbers them.
- CI judges a PR by the base branch's `.kai/config` and `.kai/tiers` (the action restores them), and the CI review reads `REVIEW.md`, `CLAUDE.md` and its agents from the base branch. Claude Code Review (`KAI_SHIP=1`) never reads `REVIEW.md` from the PR, follows its Skip list, Nit limit and lowered severities only when the default branch is protected, and cannot include a file under `.claude/agents/`. So with `--ship` the two agents are not installed, and `REVIEW.md` states their PR-side checks itself. Workflow files still run as the PR has them, so a PR can change its own checks until CODEOWNERS or a ruleset covers `.github/workflows/`.
- `/kai:accept` deletes a ticket's `docs/specs/<KEY>/`, so anything that reads specs from the base branch (`kai metrics`, gates, retros) must also work from git history or tolerate their absence. The cleanup PR passes the gates only because it changes nothing but Markdown; there is no exemption for it.
- Everything else that ends up in a user's repository lives in `plugins/kai/template/`. `kai init` writes `*.kai-new` next to a file that differs, except a workflow that differs only in its `kai-gates` or `claude-code-action` ref, which it updates in place. Keep its `CLAUDE.md` block markers unchanged, or existing repositories get a second block.
- Every skill is command-only (`disable-model-invocation: true`; `skills.bats` checks). Claude Code blocks Claude from running a command-only skill, so a skill must never tell Claude to run another `/kai:` command. Put a shared step in `references/` and have both skills follow it, or hand the command to the person. Files in `references/` are read as plain files, so they can't use `${CLAUDE_PLUGIN_ROOT}` or `$ARGUMENTS`.
- The plugin must have no `PreToolUse` or `PermissionRequest` hook on shell commands, skills, or questions to the person. `/ship` and `/steward` refuse to start a watch in a checkout that enables such a plugin or declares its marketplace, which is how `kai init` installs Kai (`install.bats` checks). That is why Kai has no Bash guard: a watch's own commits skip git hooks, so those checks belong in `KAI_VERIFY_CMDS` and CI, and a production deploy command in a `permissions.ask` rule. The hook on the edit tools only adds a notice to a watch. A watch also ends when git's configuration changes, and a worktree shares it (`git push -u` there writes it), so tell people to start the next ticket in a second clone.
- Kai ships no Claude Approvals policy. A fixed one can lock a small team, so `/kai:setup` has Claude Code's bundled `claude-approvals` skill write it, which counts the people with write access first.
- The Stop hook acts only in sessions the `UserPromptExpansion` hook marked (`session-<id>.workflow` in the git directory's `kai/`). Anything else that should act only during the workflow checks the same marker. The other hooks are safety rules and run in every session.
- SessionStart output reaches the person only through `kai_system_message`. Plain stdout from SessionStart enters Claude's context.
